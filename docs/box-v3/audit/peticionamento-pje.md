# peticionamento_pje — auditoria (revisada)

- Licença: nenhum arquivo `LICENSE` no repositório (confirmado por `git ls-files`), 8 arquivos. Sem autorização de reuso de código; aproveitamento só por CONCEITO.
- Maturidade: Python/FastAPI, commit único (2023-08-28), sem testes automatizados localizados; projeto experimental/pessoal.
- O que o código faz: expõe um endpoint HTTP `POST /upload` (`main.py:17-39`) que recebe CPF, senha, número do processo, ID da tarefa e uma lista de arquivos em base64; `src/pje_pet.py` automatiza, via requisições HTTP cruas (não Playwright) a um PJe antigo baseado em JSF/Seam (`.../peticaoPopUp.seam`), o fluxo de "Petição Avulsa": login → busca de links do processo → preparação do upload → registro do(s) documento(s) → agendamento do envio.

## Riscos graves confirmados (mantêm-se fora de cogitação)
1. **Contorno de CAPTCHA por serviço pago** — `src/pje_pet.py:14-20`: usa `anticaptchaofficial.hcaptchaproxyless` para resolver o hCaptcha do login do PJe/TJBA automaticamente, a cada tentativa de login (até 3 vezes, `pje_pet.py:24-30`). Esse mecanismo não será portado nem referenciado, exatamente como já decidido.
2. **Login por CPF/senha, não por certificado** — não há certificado A1/A3 em nenhum ponto do fluxo; a identidade é só usuário/senha, o que também não atende ao requisito de autenticação oficial do LegalOS (A1 como padrão, 2º fator supervisionado).
3. **"Sucesso" sem comprovante** — `main.py:33` retorna `{"sucesso": true}` assim que o loop de upload termina sem lançar exceção; em nenhum momento o código lê um número de protocolo, recibo oficial ou confirmação do tribunal. Continua sendo o achado mais importante: **upload de documento ≠ protocolo efetivado**, e o LegalOS nunca deve tratar um "200 OK" de upload como prova de protocolo (princípio 2 e §19 do projeto).

## Componentes aproveitáveis como CONCEITO (reimplementados do zero, sem login por senha nem CAPTCHA)
1. **Modelo de dados de entrada de uma petição avulsa** (`main.py:21`, `get_content`/`validate_content`): os campos mínimos que o PJe exige para protocolar — tipo de petição, lista de arquivos, número/ID do processo, tarefa de origem, instância — mapeiam quase 1:1 para o que `PetitionFiling`/`PetitionAttachment` do LegalOS já modelam (`prisma/schema.prisma:1044,1086`) e para os estados de `src/lib/judicial/petition-state.ts`. Confirma que o desenho de dados já existente no LegalOS está alinhado com o que o PJe de fato pede.
2. **Fluxo de petição avulsa do PJe (JSF/Seam) como referência de domínio, não de implementação**: `pje_pet.py` mostra que, nesta geração de PJe, o formulário de petição é uma máquina de estados por tela (`switch_to_screen`), cada uma dependente do `javax.faces.ViewState` da tela anterior (capturado via BeautifulSoup) e de postbacks AJAX parciais (`AJAX:EVENTS_COUNT`, `acaoAjaxAdicionarProcessoDocumento`). Isso é conceitualmente útil só para **entender** por que um robô de peticionamento no PJe precisa manter uma sessão de navegador real (cookies + ViewState vivos) em vez de requisições soltas — é um argumento a favor de usar Playwright com sessão supervisionada (como o Atrium-Senda faz) em vez de reimplementar esse protocolo HTTP cru, que é frágil a qualquer mudança de tela e já é de uma geração de PJe baseada em Seam, possivelmente obsoleta nos tribunais que o escritório usa (TRF3, TJMG, TRT15, TRT2 rodam PJe mais recente).
3. **Upload de documento com nome, mimetype e tamanho declarados** (`schedule_request`, `pje_pet.py:73-91`): confirma o padrão de que o PJe quer `{nome, tamanho, mime}` declarados antes do binário — já compatível com o que `src/server/judicial/box-v3.service.ts`/`PetitionAttachment` armazenam.

## Decisão
**APENAS CONCEITO, limitado ao modelo de dados e ao entendimento do fluxo de telas.** Nenhuma linha de código é portada. O módulo de peticionamento do Box 3.0 (ainda não implementado nesta entrega — ver `docs/box-v3-reconstrucao.md`, etapa 6) deve, quando chegar a hora: autenticar por certificado A1 (não CPF/senha), rodar em sessão de navegador supervisionada (Playwright) com intervenção humana em qualquer CAPTCHA ou 2º fator, e só marcar "protocolada" mediante recibo oficial do tribunal (`PetitionReceipt`), nunca por um upload bem-sucedido.
